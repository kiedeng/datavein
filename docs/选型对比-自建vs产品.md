# 血缘平台选型对比:自建 vs 成熟产品

配套《血缘对话平台系统设计方案 V2.1》评审使用。
评估基准:本项目五大场景(S1 溯源 / S2 影响分析 / S3 可信取数 / S4 口径答疑 / S5 元数据问答)、
银行内网私有化部署、3-5 万表规模、1 人主研兼运维、Claude Code + 门户双入口。
产品能力描述以 2025 年末社区/官方状态为准,立项前应以最新版本复核。

---

## 1. 结论(先说答案)

**维持自建,理由是需求错位而非产品不好**:市面产品(开源与商业)解决的是"数据目录 +
血缘图谱"问题;本项目的核心交付物是**对话式血缘问答与可信取数**,其差异化能力——
每跳加工表达式(transform_expr)、血缘族归并消歧、语义层确定性编译、拒答策略、
Claude Code 深度集成——**没有任何产品提供,选了产品这些仍要全部自建**。
产品能替代的只有"解析+存储+图谱 UI"一段,而这一段恰是自建代码量最小、且已验证跑通的部分
(解析内核 sqlglot 与 DataHub 官方 SQL 血缘引擎同源,技术路线业界一致)。

引入产品的实际效果是:**没减少要写的代码,反而增加一套重型系统的运维与两套模型间的
同步集成**——对 1 人主研是净负担。

**改选产品的触发条件**(满足任一,重新评估):
1. 项目范围扩大为全行统一数据资产目录(多源系统、数据 owner 门户、资产盘点考核)——
   这是产品的主场;
2. 团队获得 2 人以上平台专职编制,且行里已有 Kafka/ES 运维底座;
3. 监管或行内架构委员会强制要求采购有资质的商业产品。

## 3. 候选逐评

### 3.1 DataHub(LinkedIn 开源,Acryl 商业化)

- **强项**:业界最活跃的元数据平台;SQL 血缘同样基于 sqlglot,字段级质量好;
  ingestion 连接器丰富;UI 成熟;已有官方 MCP server。
- **致命点(对本项目)**:部署重——GMS、前端、Kafka、ES、MySQL、schema-registry,
  6+ 组件常驻,对 1 人运维是明显负担且行内需先有 Kafka/ES 底座;血缘边不携带
  加工表达式作为一等公民;消歧/语义层/取数全需外挂自建,自建部分与 DataHub 的
  实体模型(URN 体系)双向同步是持续成本。
- **适用场景**:全行数据资产目录 + 有平台小组(3 人+)时的首选开源底座。

### 3.2 OpenMetadata

- **强项**:部署比 DataHub 轻(server + MySQL + ES,可去 Airflow);Glossary 与数据
  质量模块完整;API 现代,文档好;同有 MCP 方向布局。
- **致命点**:字段级血缘解析能力弱于 sqlglot 路线(历史上依赖 sqllineage 一族),
  对 Hive 疑难 SQL(多写/自依赖/临时表穿透)的处理无本方案 5.3 的精细策略;
  同样无表达式、无消歧、无取数。
- **适用场景**:中小团队要"目录+术语+质量"一体化门户,对话能力要求不高。

### 3.3 Apache Atlas

- **强项**:Hive Hook 运行时自动捕获血缘(执行即上报,覆盖率天然高),Hadoop 系
  出身与行内 CDH/CDP 栈亲和。
- **致命点**:依赖 HBase + Solr + Kafka,运维重且技术栈老;社区活跃度持续走低,
  版本迭代慢;UI 与检索体验差;Hook 只覆盖经 HiveServer2 执行的 SQL,Spark 作业
  需另接;无表达式/消歧/取数。**不推荐新建项目采用。**

### 3.4 OpenLineage / Marquez(运行时血缘标准)

- 定位是"作业运行事件"标准而非平台:需在调度器/Spark/Flink 侧埋 emitter,
  换来的是运行时真实血缘(含每次运行的输入输出)。
- 对本项目:埋点改造面广(动每个 ETL 任务),与"制度先行、SQL 入仓解析"路线
  相比侵入性大;Marquez UI 简陋。**可作为二期实时血缘(5.5 人工通道的替代)
  的候选标准关注,不作为主路线。**

### 3.5 国产商业产品(Datablau / 亿信华辰 / 普元等)

- **强项**:交付带人驻场;信创/等保/行业合规资质全;覆盖率大盘、补录流程、
  报告输出等"管理侧"功能完善,应付检查友好。
- **致命点**:黑盒,二次开发受 license 与厂商排期约束——本项目要在血缘库上做
  消歧算法、闭包表、MCP 工具,产品库表结构不开放或不稳定即被卡死;AI 对话
  能力普遍处于"套壳问答"阶段且常绑定自家/指定模型,与自部署 DeepSeek + Claude Code
  路线冲突;license + 实施费通常为数十万至数百万人民币量级(以实际报价为准),
  与"复用现有 MySQL/Redis、零 license"的自建成本不可比。
- **适用场景**:目标是向监管/审计交付"有产品、有资质、有报告"的治理工程,
  而非做对话平台。

## 4. 三年 TCO 粗算(仅量级判断)

| 项 | 自建 | 开源产品(DataHub 类) | 国产商业 |
|---|---|---|---|
| 软件费用 | 0 | 0 | 数十万~数百万/期(报价) |
| 建设人力 | 1 人 × 14-18 周(已含对话层) | 平台部署 4-6 周 **+ 对话层仍需 1 人 × 10-14 周** + 双系统集成 3-4 周 | 实施驻场(费用内)+ 对话层同左 + 受厂商接口约束 |
| 运维常驻 | MySQL/Redis(行内已有技能)+ 3 个无状态服务 | 上述之外新增 Kafka/ES/GMS 一套 | 厂商年维保(约 license 15-20%/年) |
| 升级风险 | sqlglot 升级过金标准即可 | 平台大版本升级 + 自建部分适配双重成本 | 跟随厂商节奏 |

关键结论:因为对话层无论如何都要自建,产品路线的人力**不是替代关系而是叠加关系**。

## 6. 关于"混合路线"(产品做存储,自建做对话)的专门说明

评审常见提议:"用 DataHub 存血缘,上层自建 Agent"。不推荐,三个原因:
1. **模型不匹配**:本方案的边携带 transform_expr/filter_cond/confidence/sql_id 溯源,
   DataHub 的 lineage 模型装不下这些语义,要么塞进自定义 aspect(升级兼容风险自担),
   要么旁路再建一个库——旁路库一旦存在,DataHub 就退化成一个昂贵的 UI;
2. **闭包表与消歧算法**必须直接查库高频执行,跨产品 API 做 O(1) 连通性判断不现实;
3. 引入的收益只剩图谱 UI,而 10.2 已论证:几万表规模下图是按需下钻的导航件,
   G6 卡片两周工作量,不值得为它背一套平台。

若未来确需并入全行目录:本方案 lineage_node/edge 模型与 DataHub/OpenLineage 的
实体-边模型同构,写一个导出器把血缘作为数据源**推送给**目录产品即可——
"我们喂它",而不是"我们骑在它上面"。这也是两类系统长期共存的正确姿势。
