## 已修复漏洞

### H1(高)L3/L4 敏感维度作为过滤/排序字段绕过白名单

**问题**:编译器的敏感维度检查只覆盖 `dimensions`(SELECT 输出列)。将 L3 维度
放进 `filters` 或 `order_by` 时完全不检查白名单——`WHERE cust_no='C001'` 能精确
定位并返回单一客户的授信数据,是与直接输出同等的越权,且掩码只作用于输出列,
过滤路径的信息(是否有结果、聚合值)照样泄露客户信息。

**验证**:无 `sensitive_whitelist` 的用户提交 `cust_no` 作过滤字段 → 修复前编译通过。

**修复**(`compiler.py`):敏感检查扩展到所有对敏感维度的引用——输出列、过滤字段、
排序字段。过滤/排序引用同样要求 L3 白名单、L4 一律拒绝(不掩码因不输出,但拦截)。

### H2(高)兜底通道表集校验对无库名前缀表失效

**问题**:`run_adhoc` 的范围校验 `used = {db.name for t if t.text("db")}` 只收集
带库名前缀的表。LLM 生成 `SELECT * FROM secret_table`(无前缀)时 used 为空集,
`illegal = used - tables` 也为空,校验通过;若网关连接账号配了默认库,即可读到
圈定范围外的表,绕过"检索圈定 2-5 表"的隔离。

**验证**:无前缀表名的 used-set 为空,范围校验被绕过。

**修复**(`adhoc.py`):先检出所有无库名前缀的表引用并直接拒绝(强制全限定名),
再对全部表引用(不再过滤 `t.text("db")`)做范围校验。

### M1(中)只读通道未拦截加锁读与数据外带,黑名单大小写可绕

**问题**:`validate_select_only` 只判 `exp.Select`+单条+黑名单+LIMIT。
① `SELECT ... FOR UPDATE` / `LOCK IN SHARE MODE` 是 Select 类型,能通过校验并在
数据上加锁;② `SELECT ... INTO @var/OUTFILE` 数据外带;③ 黑名单精确匹配,
`ODS.ODS_T_CUST_SECRET` 大小写变体可绕过(Linux 下库表名大小写敏感)。

**修复**(`executor.py`):拒绝 `locks`/`into` 参数非空的语句;黑名单大小写归一化
匹配;并在 `execute` 增加 `START TRANSACTION READ ONLY` 纵深防御——即使数仓账号
误配写权限,会话层也拒绝任何写。

## 观察项(设计选择,建议行内加固)

### O1 掩码泄露首字符

`_mask` 返回 `值[:1] + "***"`,保留首字符。常见做法,但结合枚举可缩小推断空间。
H1 修复后过滤路径已封堵,风险已大幅降低。**建议**:对 id_card/mobile 等高敏字段
改为全掩码(`***`),掩码规则按 sens_level 分级可配。

### O2 EXPLAIN 预检的副作用面

`execute` 先跑 `EXPLAIN {sql}`。MySQL 8.0 的 EXPLAIN(非 ANALYZE)默认不实体化
派生表、不读取数据,风险低。**建议**:行内 MySQL 版本确认 EXPLAIN 不触发子查询
物化;保持不使用 EXPLAIN ANALYZE。

## 已确认安全的点

- **行权限值注入**:`row_policy` 变量值经 sqlglot `exp.convert` 转义,
  `O01' OR '1'='1` 被中和为字面串 `'O01'' OR ''1''=''1'`,不可注入。
- **权限缺失即拒**:`user_orgs` 缺失或空列表 → 拒绝(宁严勿松,非放行全部)。
- **plan 参数化**:LLM 只能选已声明维度,越界返回可用字段清单而非拼接执行。
- **凭据隔离**:数仓凭据仅 gateway 持有;MCP/Agent 进程无写工具、无数仓账号。
- **审计完整**:拒绝也留痕(status=refused + reason),按客户查询单独标记。
